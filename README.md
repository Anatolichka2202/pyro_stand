# Пиростенд

Qt-приложение для операторского контроля полётного задания: план из Debug КАСУ ПП,
фактические измерения относительно КП, подписанные отклонения, допуск ±1 мс и отчёт.
КАСУ ПП загружает файл в БЦВМ; пиростенд получает его и состояния через локальный
канал kasu.pp.debug.stand.v1.

## Распределение событий

Соответствие встроено по данным владельца от 12.10.2026 (распределение от Maksim
Kyznetcov). Отдельный JSON-файл подключения не нужен.

| Каналы | Назначение | Пункт БКД-А-1 | Пункт БКД-Б |
|---|---|---|---|
| 1, 2 | Пиросвечи камеры и газогенератора | 3 | 20 |
| 3, 4, 5 | Пиропатрон пусковой камеры, пусковые клапаны Г и О | 5 | 21 |
| 6, 7 | Отсечные клапаны Г и О | 16 | 24 |
| 8 | Физический КП, опорный ноль | КП только БКД-А | В текущей проводке КП нет |

Это номера действий в исходном порядке циклограммы, без START_UTC_DATE/START_UTC_TIME,
а не времена и не номера отсортированных строк таблицы. Плановые времена берутся
из полученного файла. Проверяется и назначение пункта: 3/5/16 должны содержать
IGNITE_PYRO_CANDLES_ENGINES_9_TO_12 / FIRE_STARTING_CHAMBER_ENGINES_9_TO_12 /
CLOSE_MAIN_VALVES_ENGINES_9_TO_12; 20/21/24 — IGNITE_PYRO_CANDLE /
OPEN_OXIDIZER_AND_FUEL_VALVES / SHUTDOWN_ENGINE_BLOCK_B.
Несовпадение показывается предупреждением; входы такому действию не приписываются.
В предоставленном cyclogram.txt пункт 22 — FAIRING_SEPARATION, а пункт 24 —
SHUTDOWN_ENGINE_BLOCK_B. По уточнению владельца отсечные клапаны Б привязаны к 24.

## Операторский UI (14.10.2026)

Принят тёмный поканальный макет V3. Все назначенные входы видны в группах пунктов:
вход/назначение, исходный аппаратный тик в мкс, факт относительно своего КП,
подписанная дельта и оценка. При нехватке высоты добавляются столбцы; порядок чтения
сверху вниз, затем соседний столбец. Аппаратный тик не является UTC. Диагностика
всех 96 входов остаётся в Python-приложении. Журнал доступен отдельной кнопкой.

Отсчёт до первого события и до/после КП, а также шкала двигаются плавно. После
аппаратной опоры движение между полученными отметками — индикация по монотонным
часам ПК. Измеренные факты и отчёты не интерполируются. При потере потока
индикация от аппаратной опоры останавливается.

Без физического КП относительные времена могут отображаться с `≈`, если загрузка,
разрешение и сбор подтверждены и имеются однозначные полные группы входов. Для
каждого пункта берётся медиана (тик входа − план), затем медиана опор нескольких
пунктов той же аппаратной шкалы. Разброс опор не является точностью прогноза.
Прогноз не даёт зелёной оценки допуска и не подменяет измерения в отчёте.
Неоднозначные интервалы/переполнения и повторные действия не прогнозируются.

На 1280×800 проверен набор двух старых COM: 14 пироканалов и два КП8, без прокрутки.
Для произвольного будущего объёма вместимость ограничена размером экрана; при
нехватке места показано предупреждение. Масштаб Windows/DPI тоже влияет на неё.

## Оба пиротестера

Кнопка «Подключение пиротестера» задаёт тип, COM/IP и подключённые БКД.
Выбор сохраняется в настройках Windows пользователя. При следующем запуске файлы
конфигурации и параметры командной строки не нужны. Изменение подключения
аннулирует текущий сбор: перед прогоном начать новый.

**Старый:** COM 115200, 8N1; один байт — маска восьми входов и аппаратный шаг 1 мс.
Факт = индекс байта минус индекс первого КП8. Часы ПК и размер UART-пакетов
не участвуют в расчёте. Один COM: выбор БКД-А-1 либо БКД-Б. Два COM:
первый — А-1, второй — Б; КП8 нужен в каждом потоке, поскольку начала счётчиков разные.
Без КП конкретного потока его относительный факт неизвестен.

«Начать новый сбор» очищает буферы и отметки, ждёт нулевую маску на каждом COM.
Команда сброса новой платы на старую не отправляется. Ошибка COM или обнаруженная
пауза 1,5 с делает сбор недостоверным до нового начала. У старого формата нет CRC
и номера последовательности: отдельные потерянные байты автоматически обнаружить
нельзя. Это ограничение записывается в отчёт.

**Новый:** UDP или RS-485 115200, 8N1; кадры AA55, 96 записей по 10 байт, CRC8,
итого 963 байта. Факт берётся из микросекундных отметок платы, а не времени доставки.
В диалоге выбрать ЯПС по фактическим разъёмам БКД-А-1 и БКД-Б и ЯПС с КП на входе 8.
Номера ЯПС не угадываются. Неназначенный БКД не получает оценку.

После новой циклограммы нажать «Сбросить измерения платы» и дождаться пустого кадра.
Сброс отправляется на UDP-порт платы 101 даже при приёме по RS-485. Отдельного ACK
прошивка не даёт. Активные при сбросе входы препятствуют пустому кадру.

## Текущая проводка, уточнение владельца 14.10.2026

По уточнению владельца новая плата подключена к БКД-А через группу ЯПС 8.
КП — вход 8 этой группы (внутренний индекс записи кадра: 8 × 8 + 7 = 71).
Это назначение сообщил владелец; отдельная аппаратная перепроверка пока не выполнена.
Старая COM9 подключена к БКД-Б / ЯПС 0. Физический КП есть только на БКД-А.
На старой плате в этой схеме КП не ожидается. Его случайный бит 8 не принимается
за опору. До подтверждённой привязки счётчика БКД-Б к КП другой платы точный
относительный факт недоступен; UI может показывать только расчёт по плановым
опорам с `≈`, без зелёной оценки ±1 мс. Отчёт фиксирует это ограничение.

Диалог подключения позволяет отдельно указать наличие КП в старом потоке.
Для совместного режима по умолчанию выбран профиль Б и КП старой платы выключен.
Пресет «Схема стенда» выбирает ЯПС 8 для БКД-А и КП, старый COM9 для БКД-Б,
без КП на старой плате. Назначение БКД-Б на новой плате остаётся пустым.
ЯПС в новом UI отображаются как индексы групп кадра 0..11. Старые параметры CLI
`--first-stage-yps`/`--kp-yps` сохранены: 0 — нет назначения, 1..12 — слот.
Новые `--first-stage-yps-index`/`--kp-yps-index` принимают индекс 0..11.
Не смешивать номер ЯПС БЦВМ с индексом подключённой группы тестера.

## Одновременно старый и новый

В «Подключении» выбрать новую плату (Ethernet/RS-485) и заполнить дополнительный
старый COM. Для COM9 выбрать его БКД по реальной проводке; ЯПС новой платы также
назначаются по проводке. У каждого источника свои сбор, счётчик и КП8. Оба получают
одну публикацию Debug КАСУ, а результаты показаны с подписью источника. Переход на
новый файл или перенастройка аннулируют оба сбора. «Новый сбор» обслуживает оба.
Отчёт новой платы и `<имя>.legacy.json` старой платы сохраняются раздельно, каждый
со своим `.frames.jsonl`. Нет вычисления дельты между счётчиками разных плат.

Пример при подтверждённом подключении старой платы к А-1:
```text
pyro_stand --tester udp --compare-legacy-serial COM9 --compare-legacy-block A1
```
Номера ЯПС намеренно не подставлены в пример.

## Проверки

- `ctest --test-dir build/stand --output-on-failure`: 7/7 прошли 14.10.2026.
- GUI: независимые старый/новый счётчики, отсутствие ложного допуска без КП,
  неизменность аппаратного факта при плавной индикации, весь набор входов в столбцах.
- `tests/kasu_contract/`: отдельная сборка с тем же Qt/компилятором, что КАСУ.
  Реальный `BcvmDebugModule` и два реальных потребителя `IntegrationSession`,
  синтетические события внутренней шины и входы плат. Проверены SHA/ID файла,
  подтверждение загрузки/разрешение, собственные КП и аннулирование обоих сборов.
  Это программная интеграция, не физический прогон БЦВМ.
- `-DBUILD_HARDWARE_PROBE=ON` добавляет `live_io_probe`. Он 6 секунд только принимает
  UDP/COM и Debug, не сбрасывает платы и не инициирует загрузку/исполнение.
  14.10.2026 получено 60 новых кадров и 5984 старых байта COM9, без ошибок приёма;
  Debug КАСУ в первой проверке не был подключён. Повторная проверка с запущенной КАСУ:
  оба Debug-подключения успешны, оба потока принимаются; плана и разрешения ещё нет.
  Свидетельства: `build/stand/live-io.json`, `build/stand/live-io-kasu.json`.
  Пользователь уточнил: новая плата без подключённых входов; старый COM9 подключён
  к ЯПС 0 / БКД-А 0, КП — его канал 8. КП8 в тексте — сокращение «КП на входе 8»,
  не отдельный сигнал. Название встроенного профиля А-1 не определяет физический адрес БКД.

## Развёртывание Windows

Qt 6: Core, Widgets, Network, SerialPort и Test; CMake, Ninja и соответствующий компилятор.
build.bat собирает Release в build/stand и вызывает windeployqt, если он в PATH.
Без установленного Qt переносить exe с DLL и каталогами плагинов.

Комплект создаёт package-portable.ps1 после сборки пиростенда
и КАСУ ПП Debug. С ключом `-SkipTester` упаковываются только КАСУ и пиростенд,
без приложения Егора и прошивок. Без этого ключа он размещает Qt-комплекты раздельно, добавляет готовый exe приложения
пиротестера, инструкции и справочные файлы прошивки, проверяет запуск с очищенным PATH
и создаёт ZIP с SHA-256 в build/portable. Соответствие готового exe Егора и HEX текущим
исходникам не подтверждается упаковкой. В portable-режиме настройки пиростенда хранятся
рядом с exe в settings/PyroStand/Operator.ini; режим включается файлом portable.mode.

```text
cmake -S . -B build/stand -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH=<Qt-комплект>
cmake --build build/stand --target pyro_stand
windeployqt --release --no-translations build/stand/pyro_stand.exe
```

КАСУ ПП и пиростенд запускаются на одном ПК. Для КАСУ ПП нужна Debug-сборка с модулем:
```text
kasu_pp --debug-stand-socket kasupp-debug-events-v1
```
Без параметра локальный канал не создаётся. Пиростенд по умолчанию использует это имя.
Файл проверяется по размеру/SHA-256; отдельно учитываются подтверждение загрузки
и разрешение исполнения. Разрешение не является измеренным КП. Плановый таймер UTC
по часам ПК также не является аппаратным временем исполнения.

Старый, один COM (номера портов — примеры):
```text
pyro_stand --legacy-serial COM7 --legacy-block A1
pyro_stand --legacy-serial COM7 --legacy-block B
```

Старый, два COM:
```text
pyro_stand --legacy-serial COM7 --legacy-second-serial COM8
```

Новый Ethernet:
```text
pyro_stand --tester udp --board-ip 192.168.17.144 --board-port 5000
```
ЯПС выбрать в диалоге либо параметрами --first-stage-yps, --second-stage-yps, --kp-yps.
Только фактические номера по проводке. Новый RS-485: --board-serial COM7.
В изученной прошивке адрес назначения — 192.168.17.20:5000; адрес ПК и прошивка
должны соответствовать друг другу. Python-приёмник не запускать одновременно
с пиростендом на том же UDP-порту.

## Отчёт и проверки

«Сохранить отчёт» создаёт JSON с циклограммой, состояниями КАСУ ПП, подключением БКД,
способом измерения и результатами, плюс .frames.jsonl с сырыми кадрами/масками и
идентификатором COM-потока. Это формат отчёта, не файл настройки. Сохранять оба файла.
Каждый набор измерений имеет свой `collection_id`: при смене загрузки, нового прогона,
конфигурации тестера и нажатии «Начать новый сбор»/«Сбросить измерения» старые кадры
из отчётного набора исключаются. Для двух старых COM индикация отдельно показывает
приём и КП8 каждого потока; тайм-аут любого COM делает общий сбор недостоверным.

```text
cmake --build build/stand
ctest --test-dir build/stand --output-on-failure
```

Для операторского GUI включить -DBUILD_GUI_TESTS=ON, собрать tst_operator_gui
и запустить CTest с -R tst_operator_gui. Тест работает offscreen; в среде нужны
Qt6Test.dll и offscreen-плагин выбранного комплекта.
Программные проверки не подтверждают реальную проводку, прошитую версию платы
и непрерывность старого COM-потока. Это проверяется на оборудовании.

Старые TFTP/загрузка/управление БЦВМ из пиростенда сохранены только в архивных
исходниках и [старой инструкции](docs/LEGACY_README.md). Приём старой платы
восстановлен в IntegrationSession без этих функций управления.
