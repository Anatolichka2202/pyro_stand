# Пиростенд (C++ / Qt 6)

Операторская программа наблюдения за выполнением полётного задания. **КАСУПП**
загружает циклограмму на БЦВМ; её Debug-модуль передаёт в пиростенд
исходные байты задания, идентификатор загрузки и состояние подтверждений.
Пиростенд **не отправляет команды управления полётом**.

## Возможности

- Текстовый файл `cyclogram.txt` содержит актуальные времена и подробные
  комментарии к 33 командам. Это пример/задание оператора, а не файл для автоматической
  загрузки: время `START_UTC_DATE/TIME` необходимо назначать для каждого реального прогона.
- Новая плата: кадры `AA 55`, CRC8, 96 входов, сохранённые микросекундные
  фронты и спады по Ethernet или RS-485.
- Старая плата: COM 115200 8N1; каждый байт — состояние восьми входов за 1 мс.
  Точное относительное время определяется разностью аппаратных отсчётов с КП8
  в том же потоке.
- Совместный приём новой платы и старого COM9. Это **разные шкалы времени**:
  отсутствие КП в старом потоке не позволяет выставить достоверный допуск по КП новой платы.
- Полная шкала задания; измеряемые пункты выделяются картой подключений.
  Человекочитаемые имена берутся из комментариев или каталога команд.
- Окно **«Живые каналы»** показывает восемь входов выбранной ЯПС или COM:
  текущий уровень, был ли фронт, его время, спад и длительность. Окно работает
  независимо от наличия КП, разрешения БЦВМ и возможности вычислить отклонение.
- Отдельные результаты и отчёты для разных устройств; исходные кадры сохраняются
  в `.frames.jsonl`. После завершения сбора новые кадры видны в live-окне,
  но не должны переписывать измеренный результат.

## Карта в комментариях ПЗ (`## v1`)

`KEY = OFFSET # Название для оператора ## board=NEW; link=ETH; bkd=A1; yps=9; out=1,2; in=3,4; edge=rise`

Обязательны `board=NEW|OLD`, `link=ETH|COMn`, `bkd=A1|B`,
`yps=1..12` для NEW или `none` для OLD, списки `out` и `in` одинаковой
длины с уникальными номерами 1..8, `edge=rise|fall`. Необязательный
`role=kp` обязателен для `LIFT_OFF_CONTACT`; для остальных — `channel` по умолчанию.
Пары out/in задаются по позиции, совпадение номеров не предполагается.
Несколько `##` на строке описывают несколько источников. Комментарий может быть пустым.

При наличии `##` применяется только карта исходного ПЗ, без дополнения историческими
назначениями; JSON-профиль одновременно применять нельзя. Файл и SHA-256 не меняются.
Аннотация описывает предполагаемую проводку, не подтверждает её: оценка допуска
для неё заблокирована. Полный план показывает источник и предупреждение, отчёт — всю карту.
Пустые/ошибочные поля отклоняются с номером строки. Неизвестным командам не
приписывается маска БЦВМ. Номера ЯПС в аннотациях от 1: `yps=9` соответствует
экранному индексу 8 в исторических настройках прибора.

В репозиторном `cyclogram.txt` семь аннотаций показывают историческую схему стенда,
**без подтверждения разводки**; остальные 26 действий сохранены без назначений.
Этот пример изменён явно; файлы на рабочем столе и файл, загруженный КАСУПП,
программа не редактирует. Совместимость хвостового комментария проверена по
`strtol` в исходнике БЦВМ `cyclo.c` ревизии `c8e14dc`, установленный образ отдельно не проверен.

## Операторский экран

Таблица справа и Canvas слева используют одни результаты. Под названием указаны
плановое время и источник. Нажатие строки раскрывает входы; длинный текст доступен
в подсказке. Факт группы — последний вход, Δ соответствует этому факту; статус
учитывает каждый вход, худшее отклонение доступно в подсказке и деталях.
«Последние события» раскрывают нижний журнал; полный журнал и план — в меню «Ещё».
Синий штрих на таймлайне обозначает контролируемый пункт; подсказка раскрывает кластер.
Знак ≈ у часов обозначает индикацию ПК, аппаратные результаты остаются в таблице.

## Сборка

Необходимы **CMake 3.16+**, **C++20**, **Qt 6 Core / Widgets / Network /
SerialPort / Test**, компилятор и Ninja.

```bash
cmake -S . -B build/stand -G Ninja -DBUILD_GUI_TESTS=ON
cmake --build build/stand
ctest --test-dir build/stand --output-on-failure
```

На Windows можно использовать `build.bat` с настроенными Qt/CMake/Ninja.
Для переносимой поставки — `package-portable.ps1`; он также требует отдельные
сборки КАСУПП и при необходимости программы пиротестера.

## Запуск

КАСУПП должен быть запущен в **Debug** с локальным сервером для стенда:

```text
kasu_pp.exe --debug-stand-socket kasupp-debug-events-v1
```

Примеры для пиростенда:

```text
pyro_stand.exe --tester udp --board-ip 192.168.17.144 --first-stage-yps-index 8 --kp-yps-index 8 --compare-legacy-serial COM9 --compare-legacy-block B --compare-legacy-no-kp
pyro_stand.exe --legacy-serial COM7 --legacy-block A1
pyro_stand.exe --legacy-serial COM7 --legacy-block B --legacy-no-kp
```

В интерфейсе есть пресет **«Мой стенд»** и ручная настройка источников.
Реальные адреса и ЯПС должны соответствовать монтажу стенда. Программа Егора
не должна одновременно занимать с пиростендом тот же UDP-порт приёма.

Кнопка **«Новый сбор»** для новой платы отправляет команду сброса;
её использовать только в разрешённой процедуре испытания. Кнопка
**«Завершить сбор»** завершает только программное наблюдение — **не**
отправляет команду STOP/LOCK/UNLOCK в БЦВМ.

Сбор со старым пиротестером и собственным КП заканчивается по аппаратным
отсчётам после последнего пункта циклограммы с защитным интервалом 250 мс.
Для новой платы, которая сообщает времена срабатываний, но не текущий тик,
конец окна отсчитывается таймером ПК после наблюдения аппаратного КП;
ПК **не участвует** в вычислении фактических интервалов и допуска.
Если КП отсутствует, сбор можно завершить вручную без ложной оценки.

## Границы достоверности

Подтверждение загрузки КАСУПП, разрешение исполнения и фактический сигнал КП —
разные события. Сырой фронт показывается даже без подтверждений, но
**«в допуске»** возможен только с корректным назначением канала, действующим
сбором, подтверждённой загрузкой и собственной опорой времени прибора.

Программная сборка и автоматические тесты **не заменяют испытание на железе**.
Актуальность прошитых образов, электрические назначения и точность ±1 мс
требуют отдельного подтверждения. Летняя версия для сравнительной проверки
доступна в истории Git: `bf13333` (17.08.2026). Технические решения и
история интеграции хранятся в агентской сессии `Стенд` и офисном Docmost,
а не дублируются в этом исходном репозитории.

## Испытания без оборудования

Генератор `tools/virtual_tester.py` создаёт реальные UDP-кадры `AA55` и
миллисекундные байтовые маски старого прибора, умеет воспроизводить JSONL-трассы
(`.frames.jsonl`) из отчёта и поддерживает `normal`, `missing-kp`,
`bad-crc`, `loss`, `wrap`. Он отправляет UDP **только на localhost**
и никогда не отправляет команды управления БЦВМ или сброса платы.

```bash
python3 tools/virtual_tester.py --mode udp --scenario normal --record test.jsonl
python3 tools/virtual_tester.py --mode udp --scenario bad-crc
python3 tools/virtual_tester.py --mode udp --replay test.jsonl
python3 tools/virtual_tester.py --mode legacy-file --output old.raw
```

Для live-демонстрации запустите приложение с `--tester udp --board-ip
127.0.0.1`, затем откройте «Живые каналы» и запустите симулятор. На Linux
`--mode legacy-pty` создаёт виртуальный последовательный порт и выводит
его имя (`/dev/pts/N`); приложение следует запустить на этом порте до подачи
масок. Windows-драйвер виртуальных COM в комплект не входит.

CI проверяет генератор и сквозной `tst_virtual_io`: Qt UDP-сокет, локальный
Debug КАСУПП, QSerialPort/PTY и JSON-отчёт, включая неизменность завершённой
сессии. Потери кадров без номера последовательности не обнаруживаются самим
протоколом. Синтетические проверки не заменяют аппаратную приёмку.

## Контракт КАСУПП и Windows CI

Windows CI собирает Pyro-stand под Windows x64 (Qt 6.8/MSVC) и
запускает тесты без оборудования. Отдельная задача контрактного теста с
закрытым KASU_KP по умолчанию выключена: чтобы включить, необходимо
задать переменную репозитория GitHub Actions `RUN_KASU_CONTRACT=true` и
секрет `KASU_READ_TOKEN` с правом read-only на этот репозиторий.
Обычный `GITHUB_TOKEN` Pyro-stand не имеет доступа к закрытому КАСУПП.
Исходники КАСУПП не меняются. Тест соединяет настоящий `BcvmDebugModule` с двумя
`IntegrationSession` и проверяет идентификаторы, SHA-256, разрешение
исполнения и смену загрузки; входные данные платы в этом тесте синтетические.

Локально при наличии двух соседних checkout и одинакового Qt 6.8+:

```powershell
cmake -S tests/kasu_contract -B build/kasu-contract -G Ninja -DCMAKE_BUILD_TYPE=Debug -DKASU_SOURCE=C:/qt_repos_2/KASU_PP
cmake --build build/kasu-contract
ctest --test-dir build/kasu-contract --output-on-failure
```

Никаких фиксированных путей к построенным библиотекам в CMake нет.
Для доставки релиза потребуется отдельное подтверждение переносимого
пакета и набора библиотек Qt на Windows.

## Проверка отчёта на другом компьютере

`python3 tools/verify_report.py path/to/report.json` проверяет SHA-256
архива `.frames.jsonl`, его структуру, число принятых и отклонённых кадров,
CRC8 у нового протокола и вложенную циклограмму. Работает без платы, Qt и
дополнительных Python-библиотек. Это контроль **целостности** выгрузки,
а не криптографическое доказательство происхождения данных: человек,
имеющий доступ на запись ко всем файлам, может изменить и их, и хэши.

## Пассивная приёмка на оборудовании

При `-DBUILD_HARDWARE_PROBE=ON` дополнительно собирается
`live_io_probe`. Он 6 секунд считывает данные новой платы и старого COM
и создаёт JSON-резюме с найденными физическими входами. Теперь используются
сырые `liveFrame`, а не результаты разрешённого испытания; отсутствие
циклограммы, КП или разрешения БЦВМ не скрывает фактически принятые фронты.
В CI проверяется **сборка** утилиты, но сама она там не запускается:
аппаратных подключений нет и никаких команд управлению она не отправляет.

## Windows ZIP из CI

Успешная задача **Windows / Qt 6.8 / MSVC** прикладывает ZIP
`PyroStand-Windows-x64-<commit>`. Он содержит Release-сборку
`pyro_stand.exe`, Qt-библиотеки, плагины и этот README. Отдельный
smoke-тест запускает распакованную программу с сокращённым `PATH`,
без Qt Creator и без стенда.

Это только **Pyro-stand**, а не вся система: КАСУПП Debug и физические
COM/UDP приборы поставляются и настраиваются отдельно. Прошивки,
ключи, драйверы и сторонние exe в этот артефакт не включаются.

## Контроль внешнего вида

GUI-тесты создают снимки `operator-*.png`: рабочее полётное задание,
общая шкала, сравнительный приём двух приборов и настройки. GitHub Actions
публикует снимки Linux и Windows на странице каждого прогона, чтобы
сравнивать компоновку после правок, не подключаясь к стенду. Это проверка
**отрисовки и структуры**, а не аппаратных значений и не утверждение, что
интерфейс совпадает пиксель в пиксель с летним образцом.
