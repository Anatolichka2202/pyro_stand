# Пиростенд (C++ / Qt 6)

Операторская программа наблюдения за выполнением полётного задания. **КАСУПП**
загружает циклограмму на БЦВМ; её Debug-модуль передаёт в пиростенд
исходные байты задания, идентификатор загрузки и состояние подтверждений.
Пиростенд **не отправляет команды управления полётом**.

## Возможности

- Текстовый файл `cyclogram.txt` содержит актуальные времена и подробные
  комментарии к 33 командам. Это пример/задание оператора, а не файл для автоматической
  загрузки: время `START_UTC_DATE/TIME` необходимо назначать для каждого реального прогона.
- Новая плата: кадры `AA 55`, CRC8, 96 входов, сохранённые микросекундные
  фронты и спады по Ethernet или RS-485.
- Старая плата: COM 115200 8N1; каждый байт — состояние восьми входов за 1 мс.
  Точное относительное время определяется разностью аппаратных отсчётов с КП8
  в том же потоке.
- Совместный приём новой платы и старого COM9. Это **разные шкалы времени**:
  отсутствие КП в старом потоке не позволяет выставить достоверный допуск по КП новой платы.
- Полная шкала задания; измеряемые пункты выделяются картой подключений.
  Человекочитаемые имена берутся из комментариев или каталога команд.
- Окно **«Живые каналы»** показывает восемь входов выбранной ЯПС или COM:
  текущий уровень, был ли фронт, его время, спад и длительность. Окно работает
  независимо от наличия КП, разрешения БЦВМ и возможности вычислить отклонение.
- Отдельные результаты и отчёты для разных устройств; исходные кадры сохраняются
  в `.frames.jsonl`. После завершения сбора новые кадры видны в live-окне,
  но не должны переписывать измеренный результат.

## Сборка

Необходимы **CMake 3.16+**, **C++20**, **Qt 6 Core / Widgets / Network /
SerialPort / Test**, компилятор и Ninja.

```bash
cmake -S . -B build/stand -G Ninja -DBUILD_GUI_TESTS=ON
cmake --build build/stand
ctest --test-dir build/stand --output-on-failure
```

На Windows можно использовать `build.bat` с настроенными Qt/CMake/Ninja.
Для переносимой поставки — `package-portable.ps1`; он также требует отдельные
сборки КАСУПП и при необходимости программы пиротестера.

## Запуск

КАСУПП должен быть запущен в **Debug** с локальным сервером для стенда:

```text
kasu_pp.exe --debug-stand-socket kasupp-debug-events-v1
```

Примеры для пиростенда:

```text
pyro_stand.exe --tester udp --board-ip 192.168.17.144 --first-stage-yps-index 8 --kp-yps-index 8 --compare-legacy-serial COM9 --compare-legacy-block B --compare-legacy-no-kp
pyro_stand.exe --legacy-serial COM7 --legacy-block A1
pyro_stand.exe --legacy-serial COM7 --legacy-block B --legacy-no-kp
```

В интерфейсе есть пресет **«Мой стенд»** и ручная настройка источников.
Реальные адреса и ЯПС должны соответствовать монтажу стенда. Программа Егора
не должна одновременно занимать с пиростендом тот же UDP-порт приёма.

Кнопка **«Новый сбор»** для новой платы отправляет команду сброса;
её использовать только в разрешённой процедуре испытания. Кнопка
**«Завершить сбор»** завершает только программное наблюдение — **не**
отправляет команду STOP/LOCK/UNLOCK в БЦВМ.

Сбор со старым пиротестером и собственным КП заканчивается по аппаратным
отсчётам после последнего пункта циклограммы с защитным интервалом 250 мс.
Для новой платы, которая сообщает времена срабатываний, но не текущий тик,
конец окна отсчитывается таймером ПК после наблюдения аппаратного КП;
ПК **не участвует** в вычислении фактических интервалов и допуска.
Если КП отсутствует, сбор можно завершить вручную без ложной оценки.

## Границы достоверности

Подтверждение загрузки КАСУПП, разрешение исполнения и фактический сигнал КП —
разные события. Сырой фронт показывается даже без подтверждений, но
**«в допуске»** возможен только с корректным назначением канала, действующим
сбором, подтверждённой загрузкой и собственной опорой времени прибора.

Программная сборка и автоматические тесты **не заменяют испытание на железе**.
Актуальность прошитых образов, электрические назначения и точность ±1 мс
требуют отдельного подтверждения. Летняя версия для сравнительной проверки
доступна в истории Git: `bf13333` (17.08.2026). Технические решения и
история интеграции хранятся в агентской сессии `Стенд` и офисном Docmost,
а не дублируются в этом исходном репозитории.
